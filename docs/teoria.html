1. Descrição do Projeto e Escopo Inicial

A TechFlow Solutions, empresa fictícia especializada em desenvolvimento de software, foi contratada pela startup de logística LogiFlow para desenvolver um sistema de gerenciamento de tarefas baseado em metodologias ágeis. O cliente necessitava de uma solução que permitisse acompanhar o fluxo de trabalho em tempo real, priorizar tarefas críticas e monitorar o desempenho da equipe de entregadores e coordenadores.

Escopo Inicial (Sprint 1)

O escopo original previu a entrega de um sistema web com as seguintes funcionalidades:

  • Cadastro, listagem, edição e exclusão de tarefas (CRUD completo)
  • Atributos por tarefa: título, descrição, status (A Fazer / Em Progresso / Concluído) e prioridade (Baixa / Média / Alta)
  • Interface visual em formato Kanban para visualização do fluxo
  • API RESTful para consumo por sistemas externos
  • Pipeline de integração contínua com testes automatizados

2. Metodologia Ágil Adotada

O projeto adota a abordagem Scrumban — uma metodologia híbrida que combina a estrutura iterativa do Scrum com a visualização de fluxo contínuo do Kanban. Essa escolha é justificada pela natureza do projeto: pequena equipe, entregas rápidas e necessidade de gestão visual eficiente.

Elementos do Scrum aplicados

  • Sprint Planning: tarefas planejadas em iterações semanais (sprints de 7 dias)
  • Product Backlog: coluna "A Fazer" do Kanban representa o backlog priorizado
  • Sprint Review: ao fim de cada sprint, avaliação das entregas concluídas
  • Retrospectiva: ajuste de processo com base nos impedimentos encontrados

Elementos do Kanban aplicados

  • Quadro visual: três colunas — A Fazer, Em Progresso, Concluído
  • WIP Limit (Work In Progress): máximo de 3 tarefas simultâneas em progresso
  • Fluxo contínuo: tarefas movidas conforme capacidade disponível, sem necessidade de aguardar o fim do sprint
  • Métricas de fluxo: taxa de conclusão e contagem por coluna exibidas no dashboard

3. Importância da Modelagem na Engenharia de Software

A modelagem é um dos pilares fundamentais da Engenharia de Software. Antes de escrever qualquer linha de código, a equipe precisa ter uma visão clara do sistema: quem vai usá-lo, quais funcionalidades serão entregues, como os dados serão estruturados e como as partes se relacionam. Segundo Roger Pressman (2021), "um modelo é uma simplificação da realidade que permite ao engenheiro entender o que precisa ser construído antes de construí-lo."

Por que modelar antes de codificar? Detectar erros de design na fase de modelagem custa até 100x menos do que corrigi-los após a implantação do sistema (Boehm, 1981 — ainda válido na era ágil). Diagramas UML permitem que toda a equipe compartilhe o mesmo entendimento do sistema.

Neste projeto, a modelagem cumpriu três papéis essenciais:

  1. Comunicação: os diagramas UML foram usados para alinhar a equipe e o cliente antes do desenvolvimento
  2. Planejamento: o Diagrama de Classes definiu a estrutura do banco antes de qualquer migração
  3. Documentação: os diagramas servem como referência para novos membros da equipe e manutenções futuras

O Diagrama de Classes representa a estrutura do sistema em termos de classes, atributos, métodos e relacionamentos. A arquitetura adota o padrão MVC (Model-View-Controller), onde o modelo de dados (Task) é separado da lógica de negócio (TaskService) e da interface com o cliente (TaskController).

TaskController usa Task  |  TaskController usa Database  |  Database persiste Task  |  Task herda db.Model (SQLAlchemy)

Relacionamentos

  • TaskController → Task: dependência de uso — o controller instancia e manipula objetos Task
  • TaskController → Database: dependência — o controller usa a sessão do banco para executar queries
  • Task → db.Model: herança — Task estende o modelo base do SQLAlchemy para mapeamento ORM
  • Database → Task: associação — o banco persiste e recupera instâncias de Task

6. Gestão de Mudanças — Alteração de Escopo

Contexto da Mudança

Ao final do Sprint 1, durante a Sprint Review com o cliente LogiFlow, o gerente de operações levantou uma necessidade não prevista no escopo original: visibilidade gerencial consolidada. Sem métricas agregadas, os gestores precisavam contar manualmente as tarefas em cada coluna para entender o estado da equipe — processo demorado e propenso a erros.

Mudança Implementada (Sprint 2)

Feature: Dashboard de Estatísticas em Tempo Real
Adição de um painel superior com cards de métricas consolidadas: total de tarefas, tarefas a fazer, em progresso, concluídas, alta prioridade e taxa de conclusão (%).

Justificativa Técnica

A mudança foi aceita por três razões: (1) estava alinhada aos princípios do Kanban — métricas de fluxo são essenciais para a melhoria contínua; (2) o custo de implementação era baixo (novo endpoint na API + 5 cards no frontend); (3) o campo assignee (responsável) foi adicionado ao modelo aproveitando a mesma sprint, permitindo rastreabilidade por membro da equipe.

Exemplo de teste automatizado

def test_criar_tarefa_valida(self, client):
    """Deve criar tarefa e retornar 201 com os dados corretos."""
    resp = post_task(client, 'Implementar login',
                     description='Usar JWT', priority='high')
    assert resp.status_code == 201
    data = get_json(resp)
    assert data['title'] == 'Implementar login'
    assert data['priority'] == 'high'
    assert data['id'] is not None

Importância dos testes automatizados

Cada commit que chega ao repositório aciona automaticamente o GitHub Actions, que executa a suite completa. Isso garante que novas funcionalidades não quebram comportamentos existentes (regressão) — princípio central da Integração Contínua. Além disso, a análise estática com flake8 verifica conformidade com o PEP 8 (padrão de estilo Python), mantendo a legibilidade do código ao longo do tempo.

8. Histórico de Commits Semânticos

Todos os commits seguem a convenção Conventional Commits, que categoriza as alterações com prefixos semânticos: feat: (nova funcionalidade), fix: (correção), test: (testes), docs: (documentação) e ci: (integração contínua). Esse padrão facilita a geração de changelogs automáticos e a navegação pelo histórico.

9. Questões Norteadoras

Quais são as principais causas de falhas em projetos ágeis e como o GitHub pode ajudar a mitigá-las?

As principais causas são: falta de visibilidade do progresso, comunicação deficiente entre equipe e cliente, ausência de controle de qualidade e má priorização de tarefas. O GitHub mitiga esses riscos através do Projects (Kanban) para visibilidade do fluxo, Issues para rastreamento, Pull Requests para revisão de código, Actions para CI/CD que previne regressões, e Milestones para controle de sprints.

Quem são os principais beneficiados por um sistema de gerenciamento ágil?

(1) Gestores de projeto: visibilidade em tempo real do progresso sem reuniões de status desnecessárias. (2) Desenvolvedores: clareza sobre o que priorizar, sem ambiguidade nas tarefas. (3) Cliente (LogiFlow): previsibilidade de entrega e rastreabilidade de funcionalidades contratadas. (4) Novos membros da equipe: onboarding facilitado pelo histórico de commits e documentação no README.

Como o GitHub Actions garante a entrega de software confiável?

Cada git push aciona automaticamente o pipeline: instala dependências, executa o linter (flake8) para garantir qualidade estática do código, e roda os 34 testes automatizados. Se qualquer etapa falhar, o desenvolvedor é imediatamente notificado e o merge é bloqueado — impedindo que código com bugs chegue à branch principal. Isso implementa o princípio "fail fast" da Integração Contínua.

Quais são os principais desafios ao implementar mudanças em projeto ágil?

(1) Escopo reptante (scope creep): mudanças pequenas que acumulam e desviam o projeto do objetivo. Mitigado com critérios claros de aceitação por sprint. (2) Dívida técnica: pressão por entrega rápida que leva a atalhos que degradam o código. Mitigado com code review em Pull Requests e análise estática automatizada. (3) Resistência à mudança: stakeholders relutantes em aceitar novas prioridades. Mitigado com transparência total no Kanban e métricas do dashboard.

Como as metodologias ágeis estudadas foram aplicadas diretamente neste projeto?

Scrum: sprints semanais estruturaram as entregas em iterações mensuráveis. Kanban: o quadro visual no GitHub Projects permitiu identificar gargalos (coluna "Em Progresso" cheia = WIP limit atingido). CI/CD: o pipeline automatizado implementa o princípio ágil de "entrega contínua de software funcionando". Retrospectiva: a mudança de escopo no Sprint 2 (dashboard de estatísticas) surgiu de uma retrospectiva com o cliente — demonstrando o ciclo ágil de feedback e adaptação.
